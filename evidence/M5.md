# Gate M5 · importación y copia de seguridad

**Exigía:** que reejecutar el import no duplique, que lo importado tenga procedencia y no se
atribuya al chat nuevo, que no entren claves ni ajustes, y que backup→restore se haya ensayado.

## Importación

```
npx vitest run --project unit apps/core/test/import.test.ts
→ 8 passed
```

- Entra la conversación que tiene vínculo con una sesión; la que no lo tiene se salta.
- Repetir el mismo fichero: `imported: 0`, y ni un workspace ni un mensaje de más.
- Si el workspace ya existía, se enlaza con el origen en vez de crear otro.
- El borrador sólo entra si aquí no había uno: lo de esta consola manda.
- Un export con `apiKeys`, `providers`, `mods`, `vfs` o `settings` se **rechaza entero**. No se
  limpia por detrás: quien exporta tiene que enterarse de que su volcado llevaba credenciales.
- Lo importado lleva procedencia `litechat-import` y sus mensajes viven en su propia tabla, aparte
  del transcript remoto.

## Copia de seguridad

```
node scripts/backup.mjs --core-db=.dev/core/core.db --auth-dir=.dev/gateway --out=/tmp/…
→ core.db copiada y verificada
→ almacén de autenticación copiado (3 ficheros)

node scripts/restore.mjs --from=/tmp/… --core-db=/tmp/…/core.db --auth-dir=/tmp/…
→ 4 ficheros verificados contra el manifiesto
→ integrity_check ok · esquema 4
→ contenido: {"workspaces":1,"runs":2,"events":19,"plans":0}
```

La base se copia con `VACUUM INTO`, que produce un fichero consistente aunque haya escrituras en
curso. El restore verifica los checksums del manifiesto y pasa `integrity_check` antes de dar nada
por bueno, y se niega a escribir sobre un destino con datos salvo `--force`.

## Lo que falta para el corte

Restaurar una copia del despliegue **real** en un entorno aislado y comprobar que una passkey de
verdad entra sin re-enrolar. El formato es el mismo y hay pruebas que lo fijan, pero eso hay que
verlo con el volumen real, no suponerlo.
